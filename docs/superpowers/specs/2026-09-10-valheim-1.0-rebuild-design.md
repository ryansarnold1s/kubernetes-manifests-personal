# Valheim 1.0 Rebuild — Design

**Date:** 2026-09-10
**Status:** Approved
**Target cluster:** `k8` (Talos)
**Image:** `indifferentbroccoli/valheim-server-docker` v1.0.11, pinned by digest
`sha256:3702926c5e174e4e28189136b512a034cacb9b57636c5d29d978e9a97c6e2f98` (amd64 image digest;
the tag is single-arch)
**Supersedes:** the running configuration described in
`2026-07-26-valheim-server-deployment-design.md` and `2026-07-26-valheim-bepinex-design.md`.
Both carry a correction pointing here; their content is kept as history.

---

## 1. Goal

Replace the broken Valheim server with a fresh 1.0 server on a different container image,
a fresh world, and a minimal mod set, while keeping the repo's declarative conventions:
every artifact pinned and checksummed in git, every per-mod setting expressed in a
ConfigMap, nothing hand-edited on a volume.

Non-goals: preserving the old world or any old data, carrying over the old ValheimPlus
tuning, carrying over the twelve other mods, crossplay, internet exposure.

---

## 2. Why the server is down

Established from the live pod on 2026-09-10, not inferred.

- The pod is `Running 1/1` and healthy. The game binary inside it is build
  `l-0.221.12`, network version 36.
- On 2026-09-09 15:22 the operator's client connected as `1.0.7 (network version 39)`.
  The server logged `Peer … has incompatible version` and closed the socket.
- Auto-update was disabled by design (`UPDATE_CRON: ""`), so the pre-launch build never
  moved. The lloesche image repository (now `community-valheim-tools/valheim-server-docker`)
  has an open issue from 2026-09-09, #795 "Server not updating to 1.0". Staying on that
  image would mean waiting on an upstream fix for a problem the new image does not have.
- Someone emptied the live plugins directory on 2026-09-09 11:53 while trying to recover.
  The staged copy under `/config/bepinex/plugins` and its markers were still present.

The decision to move images is therefore sound rather than a workaround: the old image
cannot currently produce a 1.0 server, and its maintenance status changed.

## 3. The new image, as read from its scripts

The README documents environment variables. The scripts are the truth. Facts below come
from `scripts/init.sh`, `scripts/start.sh`, `scripts/functions.sh` and the `Dockerfile` at
commit `cc29666` (2026-09-09).

| Fact | Consequence for this design |
|---|---|
| Game installs to `/valheim`; saves go to `/valheim-saves` via `-savedir` | The two PVCs mount there. Worlds land in `/valheim-saves/worlds_local/` |
| `PUBLIC` is dead code: `start.sh` tests `PUBLIC_ENABLED`, which nothing sets | The server is always private. Documented, not relied on |
| BepInExPack is installed **only if `/valheim/BepInEx` is absent**, and only when `BEPINEX_ENABLED=true` or `MODS` is non-empty | Any initContainer that creates a directory under `/valheim/BepInEx` before first boot suppresses the install forever, silently. See §4 |
| The doorstop env vars are chosen from `/valheim/.bepinex_version`; absent marker means "legacy 5.4.22" and the old variable names | Our installer must write that marker or BepInEx never loads |
| Default `BEPINEXPACK_VERSION` is 5.4.2333; ValheimPlus 10.0.2 depends on 5.4.2350 | We install the pack ourselves at the pinned version |
| `install_mods` runs `rm -rf plugins/thunderstore` and re-downloads every listed mod on every start, `unzip -j` flattened, no checksum | The image's `MODS` stays empty. Our directories under `plugins/<name>/` are untouched by it |
| `MAX_PLAYERS != 10` silently copies the bundled MaxPlayerCount mod into `plugins/` | `MAX_PLAYERS` is left unset |
| `init.sh` requires `PUID`/`PGID`, runs `usermod`, `chown -R steam:steam` on both volumes, then starts the game **as root** (the comment says "PID of su" but there is no `su`) | Both vars are set to satisfy the check. Root execution is recorded as a property of this image. No `runAsUser` is added; it would break the entrypoint |
| SIGTERM handler sends SIGINT to the game and waits for it | `terminationGracePeriodSeconds: 120` stays. The compose example's 30s is not enough for a world save |
| No cron, no zip backups, no adminlist handling | Backups are Valheim's native rolling set plus Longhorn plus CloudCasa. Adminlist is written by our initContainer |
| `UPDATE_ON_START` defaults false; SteamCMD runs only when the binary is absent | Game updates stay deliberate: set it true for one boot, or delete the game PVC |
| `HEALTHCHECK` uses `pgrep "valheim_server"` | Ignored by Kubernetes. Our probes are unchanged |
| `NO_BUILD_COST=true` becomes `-setkey nobuildcost` | Requested. `-setkey` persists a global key in the world save; removing the env later does not remove the key. Reversal is `removekey nobuildcost` from an admin's in-game console |

## 4. Approach chosen: the initContainer owns the whole BepInEx layer

Three approaches were considered.

**A (chosen).** The existing `fetch-mods` initContainer, slimmed, installs BepInExPack,
Jotunn and ValheimPlus into `/valheim`, writes `.bepinex_version`, applies config pins,
prunes, and writes `adminlist.txt`. The game container runs with `BEPINEX_ENABLED=true` and
an empty `MODS`.

**B (rejected).** Let the image's `MODS` fetch the mods and keep an initContainer only for
config and adminlist. Same ordering trap as above, so the config applier would need a
"skip until BepInEx exists" guard; first boot becomes a two-boot dance with an unverifiable
sentinel. Also re-downloads unverified on every boot.

**C (rejected).** No initContainer; hand-write config and adminlist onto the volume once.
Not reproducible from git.

Why A must install BepInExPack itself rather than let the image do it:

1. The image installs the pack only when `/valheim/BepInEx` does not exist. The
   initContainer runs first and must create `BepInEx/plugins/<mod>/`, which defeats that
   check on the very first boot. There is no error; the game simply boots vanilla.
2. The image reads the doorstop variable names from `/valheim/.bepinex_version`. Owning the
   install means owning that marker.
3. Version pinning. The image defaults to 5.4.2333 and honours its version env only on a
   first install. V+ 10.0.2 declares 5.4.2350.

## 6. The initContainer script

`install-mods.sh` keeps its shape and safety rails. Changes from the lloesche version:

- **Roots.** `SERVER=/valheim`, `PLUGINS=$SERVER/BepInEx/plugins`,
  `BEPINEX_CONFIG=$SERVER/BepInEx/config`, `STATE=$SERVER/.mod-state`,
  `SAVES=/valheim-saves`. One plugin root. `LIVE_PLUGINS`, the dual-root prune and the
  `sort -u` distinct-count logic are removed because there is no staged copy any more.
- **Layouts.** `plugins`, `bepinex`, `root` as before. New `pack`: extract
  `BepInExPack_Valheim/*` over `$SERVER`, then write `$SERVER/.bepinex_version` with the
  pinned version. The skip test for `pack` is marker-matches AND `.bepinex_version` exists
  AND `BepInEx/core/BepInEx.dll` exists, since there is no `plugins/<name>` dir to test.
- **Prune** walks only `$PLUGINS/*/`. The pack's `core/`, `config/` and doorstop files are
  never candidates. A loose `MaxPlayerCount.dll` would be a file, not a directory, and
  also outside the prune. The bulk breaker stays at "more than 2 in one boot" with the
  same `PRUNE_ALLOW_BULK` override and the same empty-set refusal.
- **Config applier** unchanged: same awk, same CRLF and zero-width handling, now targeting
  a real directory on the game PVC rather than a symlink into the world PVC.
- **Adminlist.** New final step: write `$SAVES/adminlist.txt` from `ADMINLIST_IDS`, header
  line `// List admin players ID  ONE per line` then one ID per line. Runs every boot;
  ConfigMap edit plus restart remains the procedure. `bannedlist.txt` and
  `permittedlist.txt` are left to the game to create.
- **Ownership.** The `chown -R 10000:10000` is removed. The image chowns both volumes on
  every start and runs the game as root.
- **Fetch tool.** The initContainer reuses the game image. It is Debian-based with `wget`
  and `unzip`; whether `curl` exists is checked at implementation time and the fetch uses
  whichever is present. `sha256sum` is coreutils and present.
- **Idempotency.** Markers keyed on `version sha256`. A normal restart downloads nothing.

## 7. Workload configuration

### `deployment.yaml`

- Both containers: image pinned by digest to v1.0.11, `imagePullPolicy: IfNotPresent`.
- Mounts: `valheim-server` PVC at `/valheim`, `valheim-data` PVC at `/valheim-saves`, in
  both containers. `mod-scripts` ConfigMap at `/scripts`, `mod-tmp` emptyDir at
  `/tmp/mods` sized 256Mi (largest artifact is 1.1 MB).
- `fsGroup` removed. `PUID`/`PGID` come from the ConfigMap.
- Game env: `envFrom` the ConfigMap; `SERVER_PASSWORD` from Secret key `server-password`.
- initContainer env: `MODS`, `MOD_CONFIG` and `ADMINLIST_IDS` by explicit `configMapKeyRef`
  (the ConfigMap also holds `install-mods.sh`, which is not a valid env name).
- Probes unchanged: `pgrep -f '[v]alheim_server'`, startup 10s × 120, readiness 30s × 3,
  no liveness. The bracket rule and its negative-case test carry over verbatim.
- `strategy: Recreate`, `terminationGracePeriodSeconds: 120`, resources unchanged
  (2 CPU / 5Gi request, 8Gi limit, no CPU limit).

## 8. Cutover

1. Connection check, same action as the scale-down.
2. `kubectl scale deploy/valheim -n valheim --replicas=0`; wait for the pod to be gone so
   Longhorn can detach.
3. Delete both PVCs. Reclaim policy is Delete; volumes and their snapshots go with them.
   **Explicit "go" from the operator immediately before this step.** No keepsake is taken;
   the operator declined one.
4. Apply ConfigMap, mods ConfigMap, PVCs, Deployment from inside `valheim/`. Each must say
   `created` or `configured`.
5. First boot. Watch the initContainer for three `[ok ]` lines and the `.bepinex_version`
   write; watch the game for SteamCMD completing, the BepInEx banner, and
   `Valheim version: 1.0.x`.
6. Label the new Longhorn volume `recurring-job-group.longhorn.io/valheim=enabled`.
7. Enumerate the generated `valheim_plus.cfg`, pick a harmless non-default sentinel, add it
   to `MOD_CONFIG`, apply, `rollout restart`. Second boot.
8. Operator joins from a 1.0 client.

## 9. Verification

Each item names its negative case, per the repo rule that a check only observed passing
has not been verified.

| Check | Pass | Negative case |
|---|---|---|
| Game version | log shows `1.0.x (network version 39)` | the old server showed 36; that line is the bug |
| BepInEx loaded | `[Message: BepInEx]` banner, Jotunn and V+ load lines | a missing `.bepinex_version` boots vanilla with no error, so the initContainer log must show the write |
| Sentinel | V+ key read back off `/valheim/BepInEx/config/valheim_plus.cfg` with the non-default value | a default-valued pin reads back correct even when the section name is wrong |
| Probe | `pgrep -f "[Z]ZZNOSUCH"` exits 1 in-container | the unbracketed form exits 0 unconditionally |
| Adminlist | `/valheim-saves/adminlist.txt` contains the ID | the file did not exist before the initContainer wrote it |
| No build cost | `-setkey nobuildcost` in `/proc/<pid>/cmdline`, then in-game | a malformed key logs nothing; cmdline proves passed, not honoured |
| Crossplay off | no `ZPlayFabMatchmaking` registration at boot | the old boot log had it on unregister |
| Snapshot label | a snapshot appears after the 11:00 job, or on demand via a Snapshot CR | a healthy-looking RecurringJob with zero snapshots is the known failure |
| Idempotency | second restart: three `[skip ]`, zero fetches | |

## 11. Risks and open items

- **Root execution** is a property of the image, accepted for a single-operator LAN
  server inside a `baseline` namespace. Revisit if the image ever adds a proper `su`.
- **Image freshness.** v1.0.7 through v1.0.11 all shipped 2026-09-07 to 09-09 in response
  to the launch. The digest pin means nothing moves under us; bumping it is a deliberate
  edit with the same recon as any mod.
- **V+ 10.0.2 on 1.0 is two days old.** If it misbehaves the fallback is to drop it from
  `MODS` and let the prune remove it; it registers no prefabs, so removal is clean.
- The old `SAVE_INTERVAL` tuning and its freeze measurements no longer apply to an empty
  world. Revisit when the world grows, using the same measurement.

**Correction (2026-09-10, whole-branch review) — three facts above were wrong or incomplete.**

1. **V+ 10.0.2's config file is `BepInEx/config/org.bepinex.plugins.valheim_plus.cfg`**, not
   `valheim_plus.cfg`. It is an ordinary BepInEx-format file (`Key = Value`) that V+ creates on
   its first boot; the V+ 10.0.2 package README says so in as many words. Every mention above
   of `valheim_plus.cfg` as V+ 10's config — the `MOD_CONFIG` sentinel in §7, step 7 of §8, and
   the Sentinel row of §9 — refers to that file. `valheim_plus.cfg` is the legacy V+ ≤9.x file:
   V+ 10 imports one once when no BepInEx config exists yet, but one found beside an existing
   BepInEx config overrides it on every launch, makes settings read-only and logs a
   deprecation warning (V+ `BepInExConfig.cs` at tag 0.10.0.2, `LegacyMode.Override`). The
   installer must never create one.
2. **§3's `MODS` row is incomplete.** The image's downloader does run on every boot:
   `start.sh` calls `install_mods` whenever `BEPINEX_ENABLED=true`, and with `MODS` unset that
   function still `rm -rf`s and recreates an empty `BepInEx/plugins/thunderstore/`. The
   installer's prune now skips that directory and does not count it toward the bulk-prune
   breaker.
3. **The digest wording is imprecise.** The pinned `sha256:3702926c…` is the tag's
   linux/amd64 platform manifest. The tag's top-level digest,
   `sha256:e026a00ee3f4dcd92a07de40003aae270f6aa25583b27bbe6fafc551daec58aa`, is an OCI image
   index whose only other entry is a build attestation manifest, so "the tag is single-arch"
   holds for platforms but not for the manifest shape. Pinning the platform digest is still
   correct.
4. **`SAVE_DIR` is now pinned** in `valheim/configmap.yaml` (`/valheim-saves`) instead of
   being left to the image's Dockerfile default, because the `-savedir` arg, the PVC
   mountPath and the installer's `SAVES` default must all agree.
